## Findings

**High** · `app/server.mjs:60-65` — this compensates for the bug rather than removing it. The mechanism in issue 001 is *a write that lands before the decision is final*: `item.stock -= qty` executes at line 60 while a guard that can still reject the order sits at line 62. The patch leaves that write exactly where it was and adds `item.stock += qty` to undo it on the one reject path that now runs after it. `AGENTS.md:33` — "If a one-line patch makes the test green but leaves the mechanism that produced the bug in place, it is the wrong patch" — and `prompts/fix.md:2` — "If your change makes the test green while leaving that mechanism in place, it is the wrong change: name it and fix the mechanism instead" — both name this shape directly. `AGENTS.md:34` ("no silent failures, no partial success") is the third: the reject path now performs a partial write and silently reverses it.

*Failure scenario:* the demonstrable half is the test side. `test/orders.test.js:80-85` enumerates today's four rejection reasons as a hard-coded list, and `npm run req-coverage` only checks that some test names each REQ id — it cannot see that a fifth reason has no case. So the next guard added to `createOrder` (a per-SKU daily cap, a "discontinued item" check, a fraud hold) lands below line 60 by imitation, because the file now shows a guard living below the write and being cleaned up afterwards. That guard rejects, stock drops, REQ-ORD-4 is broken again — the same 47 → 22 in issues/001 with a different reason string — and `npm run verify` stays green. The author of that guard has to remember a compensating write that nothing enforces and no test would miss.

*What to do:* move `item.stock -= qty` below the last guard instead of undoing it after the fact. Guard order is unchanged by that, so every rejection reports the same `reason` it does today, and the invariant stops depending on anyone remembering to roll back.

*Confidence:* high on the patch shape, and high on there being **no reproducible runtime defect today** — I checked, and say so plainly. `createOrder` is fully synchronous with no `await` between line 60 and line 65, so no concurrent request can observe the torn stock value. The severity comes from the repo's stated rule about patch shape, which exists here and names this exact failure mode, not from a wrong response I can show you.

**Q2, answered straight: there is no second existing path built this way.** `createOrder` is the only function that mutates `items`, `orders`, or `nextOrderId`; `orders.push` and `nextOrderId++` already sit on the success side of the last guard. **Low-medium** · `app/server.mjs:58` — reason precedence between REQ-ORD-2 and REQ-ORD-3 is unspecified, untested, and unmentioned. `prompts/fix.md:10` (rule 4, "check the neighbours … even if no test covers them") asks the fixer to report exactly this, and nothing in the change does.

*Failure scenario:* observed — `createOrder('PEN-1', 21)` against the seeded stock of 8 returns `{"reason":"insufficient_stock"}`. Both WHEN clauses match that input: REQ-ORD-2's, and REQ-ORD-3's unqualified "WHEN 21 units are ordered THEN the response is `422` with `{"reason":"over_limit"}`". Note that REQ-ORD-3's *other* scenario says "WHEN exactly 20 units are ordered **and stock allows it**" — the qualifier is present there and absent on the 21-unit case, which reads as deliberate. Both readings reject the order and both return 422, so only the `reason` string differs; but that string is the explanation the shopper gets, and one told `insufficient_stock` will retry with a smaller quantity that is still over the cap.

*Confidence:* low-medium, and this is an interpretation call, not established drift. "Regardless of stock" most plainly means the cap bites even when stock is ample, and under that reading the code is correct — the spec never says which reason wins when both apply. What is missing is a sentence in the fix report saying which reading was chosen, and a test that pins it. No test in `test/orders.test.js` covers a >20 order on a low-stock item, so a future reorder of lines 57-58 changes user-visible behaviour with the gate still green.
